# LiteWing outer-loop storage correction

This is a source-only correction of the selected Stabilization outer loop.
It does not change the installed firmware or its last-recorded Always Disarmed
setting. No serial access, reset, flash, arming, motor operation or live AI call
is included. Overall startup, physical cutoff, battery and flight gates remain
open; source correctness is not physical flight clearance.

## Reproduced defects

The pinned NinjaPilot `outerloop.c` has `AXES == 4`, but outside `SIMPOSIX` it
allocates two three-float arrays. Its per-axis loop reaches Thrust at index 3.
The complete original module, real generated UAVObjects and real PID/quaternion
libraries reproduce this diagnostic in both direct and attitude execution:

```text
outerloop.c:286:38: runtime error: index 3 out of bounds for type 'float[3]'
```

The initial fixture had missing host-boundary declarations/linkage. Those were
corrected before accepting the behavioral red result; build errors did not
count as a reproduction. Permanent original-source controls require this exact
index/type diagnostic (allowing GCC's whitespace), not any crash or error.

The first real ESP32-S3 build also diagnosed passing `&attitudeState.q1`, a
packed scalar field, to `quat_mult` as a four-float array. A stricter real SDK
compiler invocation rejected this with `-Werror=address-of-packed-member`.
The quaternion path similarly indexed the address of the scalar Roll field.
These packed-struct fields are copied to bounded local float arrays now.

## Adaptation contract

`prepare_stabilization.py` validates the full upstream file SHA-256 before
changing a build-directory copy:

```text
a89228f3c6a3700cccb41b35bcf886672e901c6b18c6c851f11fcbeeaa9bb314
```

- Both desired/rate buffers contain four explicit Roll/Pitch/Yaw/Thrust entries.
- Quaternion math uses explicit three-element RPY and four-element quaternion
  arrays, without converting packed scalar fields to array pointers.
- Direct thrust publication remains `rateDesired.Thrust = stabilizationDesired.Thrust`.
  No altitude controller or new thrust mode is introduced.
- Compile guards reject `SIMPOSIX` and `REVOLUTION`; static assertions check
  four axes and the Thrust index. Simulator behavior is not globally enabled.
- Input/output separation, input identity and output-symlink/hardlink checks precede
  generation. Repeating unchanged generation preserves the output timestamp.
- Original GPL notices and the external checkout are preserved.

The real CMake component selects only the generated `outerloop.c`, watches the
generator/helper/upstream inputs, and rejects adaptation failure. The generated
SDK command/graph tests check that selection and compare generated bytes.

## Verification scope

The full consumer fixture runs the real attitude-update callback and its
four-update decimation, captured scheduler callback, outer-loop implementation,
generated object accessors, PID, coordinate conversion and delta-time code.
The object store, clock, scheduler and cruise-control handoff are controlled
host boundaries. This is not a FreeRTOS timing or hardware test.

Direct mode, independent roll/pitch/yaw attitude cases, and mixed cases with
one direct current-attitude component publish all four
RateDesired fields over thrust inputs `0.375`, `0`, `-1` and `1`. Attitude cases
use a non-identity quaternion and a known single-axis five-degree error with
gain two. Each callback cycle must publish once, replacing distinguishable
stale outputs; cruise-control receives the same attitude and published thrust.
Neither cruise-control internals nor downstream electrical output are verified.

Tests deliberately revert either corrected buffer to three entries, omit each
output field, and omit each current RPY/quaternion component. Two bounds mutations
must produce the sanitizer diagnostic; eleven value mutations must fail explicit
behavior assertions. Four original-module executions retain the bounds red
control. Adapted host builds retain `-Werror`; only the original GCC control
permits its known string-overread warning so it can reach the runtime defect.

Independent review reproduced an output-hardlink path that could mutate the
pinned input. A permanent regression now requires rejection and byte preservation;
the generator rejects non-regular or multiply linked existing outputs before
reading or writing them. Review also showed that zeroing all copied current RPY
values escaped the initial single-axis cases. Three mixed-mode cases plus the
original all-zero and individual Pitch/Yaw mutations now cover the observable
behavior. Changing only the copied Roll value when Roll is direct changes only
the ignored direct-axis error; the exact initializer remains source-checked,
without claiming an output distinction that the algorithm does not expose.

Three optional real SDK checks verify the selected source/build dependencies,
quaternion/non-simulator feature selection and 4096-byte stack parity, and
strict packed-member/string-overread diagnostics with an original-source
negative control. CI runs source-backed host tests; without a supplied ESP-IDF
graph it explicitly skips these SDK checks. It is not ESP32 firmware CI.

These tests do not establish all stabilization modes, gain tuning, full startup
readiness, object-read failure handling, live sensor validity, safe arming,
watchdog cutoff timing or flight behavior. Remaining Stabilization/Telemetry
startup internals still need work under the broader port goal.

## Reproduction

With the pinned NinjaPilot checkout and generated flight UAVObjects:

```sh
export LRRK_TEST_FLIGHT_ROOT=/path/to/NinjaPilot
python3 -m unittest discover -s ports/ninjapilot-litewing/tests -p test_outerloop_bounds.py -v
python3 -m unittest discover -s ports/ninjapilot-litewing/tests -p test_stabilization_preparation.py -v
```

For the SDK-specific checks also supply `LRRK_IDF_BUILD_DIR` pointing to the
actual ESP-IDF build and `LRRK_NINJA` if Ninja is not on PATH. Build with the
documented ESP-IDF 5.3.2 environment. Do not run the flashing commands printed
by `idf.py build` as part of source verification.
